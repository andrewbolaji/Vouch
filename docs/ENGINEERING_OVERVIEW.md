# Vouch engineering overview

This is a map of why the code is shaped the way it is, for someone with read access who has never seen the repo. Every claim points at the file and symbol behind it, `path/to/file.ext :: symbolName`. Where a doc in this repo disagrees with the code, the code wins and the disagreement is recorded, not resolved quietly. Where no rationale for a decision could be found in a comment, a commit, or a doc, that is stated plainly instead of invented.

This repo carries two whole-repo handover documents; if you are holding both, here is which is which. This one, `ENGINEERING_OVERVIEW.md`, is the map of why the code is shaped the way it is, meant to orient a reader before they start changing things. `docs/IMPLEMENTATION_RATIONALE.md` is a differently structured, more mechanical document built for a specific external review process (invariant/failure-behavior tables, a verification-performed log with actual commands run, a known-compromises table with owner and revisit-trigger columns), written to that process's fixed template rather than for general orientation. They overlap in subject matter on purpose; read this one first if you are new to the repo, read that one if you are the reviewer that template was built for.

## Prerequisites and what you cannot exercise without credentials

`CLAUDE.md :: Gotchas` is the fastest orientation to setup. `flutter test --exclude-tags=golden` needs no credentials, but the Firestore/auth emulator suites need Java on `PATH` and `firebase emulators:exec`. `lib/firebase_options.dart` is gitignored and generated by `flutterfire configure`; without it, `flutter analyze` reports 4 errors and the app will not build, though `flutter test` still passes. `functions/package.json :: engines.node` pins Node 22; a local Node 20 only matters to `firebase deploy`.

Three things here cannot be confirmed from the repo at all: Firebase console App Check enforcement status (Section 6), Firestore point-in-time recovery and delete-protection settings (Section 11), and live RevenueCat dashboard configuration (Section 7). Seed scripts that call the Google Places API need `GOOGLE_PLACES_API_KEY`; admin scripts need `GOOGLE_APPLICATION_CREDENTIALS` for a service account with access to the target project. None of that is in the repo, deliberately.

## 1. How to read this repo

`CLAUDE.md` first: run commands, an architecture map, and a Gotchas section that exists to stop known traps. `docs/DECISIONS.md` second, the only place in the repo where rationale for non-trivial choices is recorded on purpose, dated, with what was tried and rejected. `pubspec.yaml :: dependencies` third, for a fast dependency inventory, including the Flutter tool defaults it deliberately disables (`pubspec.yaml :: flutter.config`). Then `lib/main.dart :: main` and `:: VouchApp.build`, which show the real bootstrap order and the full provider tree in one place. Then `lib/providers/app_state.dart :: AppState`, the 624-line `ChangeNotifier` most screens read through. Finally `firestore.rules`, best read last since by then you know what data shapes it protects; `CLAUDE.md :: Architecture map` states this file, not client code, is the real trust boundary. This ordering is my judgment call, not something the repo states, and is flagged as such.

## 3. Data model

The client models under `lib/models/` are ground truth here, not `docs/FIRESTORE_SCHEMA.md`, self-labeled "Design doc. No code" and wrong about the implementation in several places noted below.

| Collection | Shape | Denormalized field | Sync mechanism |
|---|---|---|---|
| `cities/{id}` | `lib/models/city.dart :: City` | `restaurantCount` | None found. The schema doc claims a Cloud Function keeps it in sync; no such trigger exists in `functions/src/index.ts`. Only seed scripts set it, once. |
| `restaurants/{id}` | `lib/models/restaurant.dart :: Restaurant` | `voteCount` | Two mechanisms now. One drift already exists: `lib/data/seed_data.dart :: SeedData.restaurants`, the offline fallback `AppState._loadFromFirestore` falls back to on any read failure, hardcodes Atlanta IDs as `atl-1`...`atl-17`. The real seeder, `scripts/seed_atlanta.js :: writeAtlantaData`, assigns IDs from the Places ID or a slugified name instead. Names still line up; IDs do not, so anything keyed by ID against the fallback data will not resolve against the real documents. `scripts/seed_production.js`'s hardcoded `cities` array also omits Atlanta entirely, while `lib/data/seed_data.dart` includes it.

## 4. The ranking system

The decay function is `functions/src/rank_engine.ts :: computeScore`: each vote contributes `weight * exp(-decayRate * ageDays)`, `decayRate = Math.LN2 / halfLifeDays`, age clamped at zero. Half-life is `DEFAULT_HALF_LIFE_DAYS`, a literal 90. The age clamp is deliberate: `rank_engine.test.ts`'s "a future-dated vote cannot outrank a fresh vote" states in its own comment this is a second layer behind the `createdAt == request.time` rule.

`functions/src/rank_recompute.ts :: recomputeAllRanks` is the orchestrator. For every city, every restaurant, it reads the full `votes` subcollection, scores, sorts, and calls `rank_engine.ts :: assignRanks` for contiguous ranks. It batch-writes `rank`, a rounded `rankScore`, and, since 2026-08-12, the true `votes` subcollection size back into `voteCount` in the same batch (see Section 3), and warns if a restaurant moved more than 5 positions since the last run, or every score in a city rounds identical with more than one restaurant present (`:: logCitySummary`). It runs on a schedule, not a trigger: `functions/src/index.ts :: recomputeRanks` is `onSchedule({schedule: "0 6 * * *", timeZone: "UTC"})`, daily at 06:00 UTC.

Ranking recomputes on a schedule instead of live on every vote because the product promises this cadence publicly: vouchfood.com's Integrity section states "the order recalculates every morning, so the list holds still while you read it instead of jumping around" (`docs/DECISIONS.md`, 2026-08-12 entry, which records this rationale for the first time; the 2026-06-11 entry above it had recorded the schedule itself but not why it was a schedule and not a live update). A live recompute would break that promise, the list would visibly reorder mid-read. A separate, unrelated rationale exists for a future change to how the computation scales, not to its cadence: `docs/DECISIONS.md` also records a plan to switch from reading every vote doc at recompute time to an incrementally maintained counter once a restaurant passes 500 votes, to avoid O(N) reads.

Casting a vote updates `voteCount` and writes a `voteEvents` record immediately, deliberately in that order (`functions/src/index.ts`, comment: the audit write "must not depend on the aggregation succeeding first"). The restaurant's position does not move until the next 06:00 UTC run. `rank_engine.test.ts`'s "exact rank order across the decay curve" asserts a full tie-break chain, score then vote count then alphabetical name, on an exact fixture.

Distinct from computed rank, `scripts/set_houston_launch_order.js` and `set_atlanta_launch_order.js` hand-write a launch-day `rank`/`displayOrder` onto the same field the nightly job owns; that order is only authoritative until the next recompute. `lib/models/restaurant.dart :: kUnrankedRank` (9999) is the sentinel new restaurants get, and `docs/DECISIONS.md` states it is meant to be overwritten once votes arrive.

## 5. Vote integrity

What an attacker can and cannot do is enforced in `firestore.rules`, proven by `test-rules/src/firestore.rules.test.ts` rather than just the rule text. A client can vote once, at their own UID as the doc ID (`match /restaurants/{restaurantId}/votes/{userId}`), cannot vote as anyone else, cannot set `weight != 1`, cannot back- or postdate `createdAt` (must equal `request.time`), and cannot mutate an existing vote, only delete and recreate it. An unverified email cannot vote at all. Ranks 1 to 5 are public reads; 6 to 10 require an authenticated, paid-tier reader, checked server-side against the doc's own `rank` field.

`voteEvents` is append-only by rule (`match /voteEvents/{eventId}` denies all client reads and writes, including to the user the event is about); no deeper rationale beyond it being an audit trail was found. It is written from Cloud Functions because the client has no path to it at all: the vote triggers (`onVoteCreated`, `onVoteDeleted`) call `vote_audit.ts :: recordVoteCreated`/`recordVoteDeleted` before the vote-count aggregation, deliberately, so a fabricated `restaurantId` is caught even if aggregation never gets there. Dedup is a deterministic document ID, not a query: both write to `voteEvents/{event.id}` using the trigger's own delivery ID, so an at-least-once retry overwrites rather than duplicates, proven by `vote_audit.test.ts`'s "a duplicate eventId does not produce two records." When the restaurant lookup for `cityId` fails, `vote_audit.ts :: lookupCityId` never throws, it returns `null`, and the event writes anyway. This is by design: the file's comment cites a real incident, 163 fabricated vote documents found in production on 2026-08-07 under restaurant IDs with no restaurant document at all (`scripts/README.md`).

Votes are current state, not history. A vote doc is created once and deleted on unvote with no update path, so once deleted it is gone from `votes` entirely; `functions/src/user_cleanup.ts :: deleteUserData` permanently deletes a departing user's votes the same way. The only durable record is `voteEvents`. As of 2026-08-12, `functions/src/vote_audit.ts :: recordVoteCreated`/`recordVoteDeleted` capture `weight` too, read from the vote document that triggered the event, so a `voteEvents` record going forward carries everything the ranking engine's `computeScore` needs to reconstruct a vote's contribution. Events written before that change still lack the field; `scripts/backfill_vote_event_weight.js` sets `weight: 1` on any `voteEvents` doc missing it, lossless because security rules have always forced `weight == 1` at vote creation, and only lossless today, this would not be correct once verified-visit weighting (`weight > 1`) ships. No script reads from `voteEvents` for recovery even now; the one real incident on record was found by a different, purpose-built diagnostic against the live `votes` collection group (`scripts/check_vote_timestamps.js`) and fixed by manual, per-path deletion, not audit-log replay.

## 6. Auth, App Check and App Attest

Providers wired up: anonymous, email/password, Google, Apple, all in `lib/services/auth_service.dart :: AuthService`. App Check is activated in `lib/main.dart`, App Attest for iOS release, Play Integrity for Android release, debug provider gated behind `kDebugMode` and compiled out of release. The current state, not the intended one: activation only attaches attestation tokens, it does not require them. A repo-wide search for `enforceAppCheck` returns zero matches in `functions/src/index.ts`, and the comment above the activation call says so outright: "App Check: monitor-only (enforcement is a separate console step)." `docs/HANDBOOK.md` corroborates: "unverified requests still succeed." Whether the console's per-API enforcement toggle has since flipped in the live project is not visible from this repo.

## 7. Purchases and the paywall

Membership tier is set in two places by one function: `functions/src/membership_webhook.ts :: handleWebhookEvent` sets the Auth custom claim first (rules read that, not the Firestore field), then writes `users/{uid}.membershipTier` to match. Triggered by `functions/src/index.ts :: onRevenueCatWebhook`, which authenticates the caller by comparing the `Authorization` header to a Secret Manager value (`:: isValidAuth`). As of 2026-08-12 that comparison is `crypto.timingSafeEqual`, not `===`, with an explicit length check first since `timingSafeEqual` throws a `RangeError` on mismatched buffer lengths rather than returning false; `isValidAuth` is called before `onRevenueCatWebhook`'s own `try` block starts, so an unguarded throw there would have surfaced as an uncaught 500 instead of a clean 401, and RevenueCat retries a 500 but not a 401 (`functions/src/index.test.ts`, "different-length wrong secret rejected, does not throw"). RevenueCat does not sign webhooks, so there is no signature scheme to move to instead; the shared secret in the header is their documented mechanism. What the timing fix does not address: `handleWebhookEvent` still has no defense against a replayed or out-of-order event, it derives tier solely from the incoming event's own `type`/`entitlement_ids`, with no timestamp or sequence check against what is already stored, so a stale `RENEWAL` arriving after a `CANCELLATION` has already reset a user to free would silently set them back to paid. On the client, `lib/providers/membership_provider.dart :: MembershipProvider` derives gating booleans consumed by `lib/widgets/paywall_gate.dart :: PaywallGate`. This is backed independently server-side: `firestore.rules` reads the same custom claim to restrict ranks 6 through 10 and insider notes, so a patched client cannot unlock either by lying about its tier, only by holding a valid claim.

## 8. Comments

`functions/src/index.ts :: submitComment` is the only path that can create a comment; `firestore.rules` denies direct client creates outright, proven by a rules test named exactly that. Filtering (`functions/src/moderation.ts :: containsBannedContent`) is a third-party base dictionary (`leo-profanity`) plus a hand-written harassment-phrase list, matched with an explicit word-boundary regex rather than the library's own substring check, to avoid false positives like "Scunthorpe." What it does not do: no rate limiting on comment submission anywhere, unlike suggestions, which cap at one per day; a user can post as fast as the network allows. The 500-character cap lives in `submitComment` itself, not `moderation.ts`. `submit_comment.test.ts`'s "derives userName from the user doc, not client input," added specifically to close a gap (commit `b9a116b`: "Nothing proved that until now"), confirms a client cannot post as "Admin." Replies are still one query per comment per page load (`app_state.dart :: _fetchRepliesFor`, parallel via `Future.wait`); a proposed `replyCount` field to skip that call does not exist in `comment_aggregation.ts` or the `Comment` model.

## 9. Client architecture

State management is the `provider` package: every state class extends `ChangeNotifier`, wired via `MultiProvider` in `lib/main.dart :: VouchApp.build`. Data flows from a repository (`restaurant_repository.dart :: RestaurantRepository.getForCity`) into `AppState._loadFromFirestore`, exposed through `AppState.restaurantsForCity`, read via `context.watch<AppState>()`. Vote casting is optimistic: `AppState.toggleVote` mutates local state and calls `notifyListeners()` before the write resolves. No code configures Firestore's offline persistence or cache size explicitly, so the SDK default applies; whether that was deliberate or never considered cannot be determined either way. Errors are a sealed hierarchy, `lib/core/error/app_exception.dart :: AppException`, stated intent "raw Firebase exceptions never reach the UI," converted by `firestore_exception_mapper.dart :: mapFirestoreException`. Call sites diverge: `SavedProvider.toggleSaved` rolls back and returns the exception, `SuggestionProvider.submitSuggestion` rethrows after local bookkeeping, `AppState._loadFromFirestore` swallows it, sets an offline flag, and falls back to `lib/data/seed_data.dart`. On a cold start with no network, `SplashScreen` navigates on schedule since it makes no network call, and `HomeScreen` shows a shimmer while loading and an offline banner if the read fails. What cannot be confirmed: no repository call wraps its Firestore read in an explicit timeout, so whether a `.get()` with no connectivity and no cache fails fast or can hang is not something a static read can settle; it needs running the app offline to check.

## 10. Testing

`test/goldens/` is five component fixtures, not screen renders. `primitives_golden_test.dart` renders single widgets, rank chips, buttons, a badge, a toggle pill, on canvases as small as 390 by 120 pixels; `card_golden_test.dart` renders three `RestaurantCard` widgets in a bare `Scaffold`. No file there instantiates a screen class. `test/goldens/golden_harness.dart :: setUpGoldens` mocks `path_provider` and swaps `sqflite` for FFI, purely so `CachedNetworkImage` does not throw headless; its docstring now correctly states baselines are CI-authoritative, generated and validated on `ubuntu-latest` by `.github/workflows/update-goldens.yml`, not on a developer machine, matching `CLAUDE.md :: Gotchas`. It previously claimed the opposite ("validated on this machine (macOS arm64)"); fixed 2026-08-12. Measured directly this session: `flutter test --tags=golden` fails all 5 locally on macOS arm64, exactly the platform mismatch the comment now describes.

`test/interactions/` is where multi-step flows live: `city_detail_interaction_test.dart` toggles Top 5/Top 10 and asserts a `PaywallGate` appears for a free user, checking gated names are absent from the widget tree, not merely styled invisible. Everything else is conventional: pure round-trip tests in `test/models`, state-transition tests against fakes in `test/providers`, Firestore shape assertions against `fake_cloud_firestore` in `test/repositories`. On functions, `rank_engine.test.ts` asserts an exact golden order across a 7-restaurant fixture; `vote_audit.test.ts` proves the dedup and null-`cityId` behavior in Section 5; `test-rules/src/firestore.rules.test.ts` runs every scenario in Section 5 against the real emulator. Not covered: push notifications (`lib/services/notification_service.dart` is an explicit `TODO` stub, no test file), the RevenueCat webhook's lack of signature verification (there is no signature check to test, only the shared-secret comparison, which is tested), and the native `GoogleSignIn` flow, deliberately excluded per a comment in `auth_service_test.dart` since it calls the platform SDK directly, with no device or integration test in this repo to cover it instead.

## 11. Operations

Hosting and functions deploys are both manual; `.github/workflows/ci.yml` runs tests and `flutter analyze` but has no `firebase deploy` step, and `functions/package.json :: scripts.deploy` is a local npm script CI never invokes. Because they are manual they can be done in the wrong order, so the order is a standing rule (`docs/DECISIONS.md`, 2026-08-13): functions and rules first, app build second. A build that reaches devices before its triggers are live reads fields nothing is writing yet, and for `votedRestaurantIds` specifically, votes cast in that window enter no user's list and are recovered only by running `scripts/backfill_voted_restaurant_ids.js` by hand. Cache headers (`site/firebase.json :: hosting.headers`) serve HTML and `/` as `no-cache`, static assets as `public, max-age=31536000, immutable`; commit `af2c397` added this after HTML served with an hour-long cache, meaning a deploy could take up to an hour to reach a returning visitor. Firestore PITR and delete protection are not configured anywhere in this repo, no Terraform, no gcloud script; if either is enabled it is console-only and unverifiable here.

Every write-capable script in `scripts/` gates behind `--confirm` and defaults to a dry run. As of 2026-08-12 this includes `scripts/backfill_comment_counts.js`, which previously had no confirm flag or dry-run mode and wrote to every restaurant doc the instant it ran; it also had its own credential logic (an explicit `cert()` when `GOOGLE_APPLICATION_CREDENTIALS` was set, no confirmation gate, silent hardcoded `"vouch-dev"` fallback otherwise) instead of the shared `admin.initializeApp()` pattern every other script uses. Fixed by dropping the special case entirely: the resolved project now always prints for a human to check, and a write always needs `--confirm`, the same guardrail every other script in the directory already had. `scripts/reset_votes.js` deletes every vote for every restaurant behind nothing but the confirm flag, no project allowlist. Seed scripts hardcode `status: "live"` or `"comingSoon"` per city and `voteCount: 0` on every new restaurant; `set_houston_launch_order.js`/`set_atlanta_launch_order.js` hardcode launch-day rank and, in Houston's case, a list of restaurant names to delete outright.

That deletion path was the traceable root cause of the 163-document incident in Section 5: it batch-deleted a restaurant document without walking and deleting its `votes` subcollection first, so a removed restaurant's votes could survive it. Fixed two ways as of 2026-08-12. At the script level, `scripts/lib/cascade_delete.js :: cascadeDeleteRestaurant` now walks and deletes `votes`, `comments`, and `insiderNotes` before the restaurant doc, used by `set_houston_launch_order.js`'s removal path (`set_atlanta_launch_order.js` has no delete path at all, it only ever updates `rank`/`displayOrder`, so it was never actually part of this bug despite being named alongside it when the fix was requested). Structurally, `functions/src/index.ts :: onRestaurantDeleted`, a new Firestore trigger backed by `functions/src/restaurant_cleanup.ts :: deleteRestaurantData`, does the same cleanup for every restaurant deletion regardless of source, not just the one script that caused the 2026-08-07 incident; a future script or a manual console delete gets the same protection. `scripts/scan_orphaned_docs.js` is a one-off `collectionGroup` scan for any vote or comment document whose parent restaurant no longer exists, dry run by default, for finding orphans that predate either fix.

## 13. Where I most want your eyes

Whether the newly deployed `onRestaurantDeleted` trigger and `set_houston_launch_order.js`'s cascade delete (Section 11) actually behave the same way in production as they did against the emulator this session, since a trigger can only be exercised for real by an actual restaurant deletion. Whether `commentCount`'s lack of reconciliation, now that `voteCount` has one (Section 3, 12), should get the same nightly fix or was deliberately left out for a reason worth stating explicitly rather than leaving as an asymmetry. Whether the lack of a client-side timeout on the first Firestore read in `AppState._loadFromFirestore` (Section 9) can actually hang a cold start offline rather than fail fast needs running the app with no network, not just reading it. Whether App Check enforcement (Section 6) has actually been flipped on in the live console since the code and docs were last touched, since the repo cannot answer that.
